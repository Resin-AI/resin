# Canonical Architecture Glossary

This document establishes the canonical terminology and definitions used across the Resin architecture, codebase, decision records, and API contracts. All documentation, code symbols, and error messages must adhere to these definitions.

---

### Activation
The atomic operation of registering a specific **Tool Version** with the **Gateway**'s routing table to begin serving live requests. Activation can occur in **Canary** mode (traffic splitting or shadow execution) or **Promoted** mode (active default).

---

### Audit Log
An immutable, append-only, tamper-evident cryptographic ledger (HMAC-SHA256 and Merkle chaining) stored in the local SQLite database recording all tool lifecycle state changes, capability grants, policy violations, and data synchronization events. See [ADR 0005](../adr/0005-privacy-data-boundaries.md).

---

### Candidate
A newly synthesized or proposed **Tool Version** generated by the **Evolution Engine**. A Candidate must successfully pass static analysis, AST security verification, and automated contract tests before it can transition to a **Canary** activation.

---

### Canary
An intermediate deployment state where a **Candidate** tool version receives a controlled subset of live traffic (e.g., 10% traffic split) or executes in background shadow mode alongside the existing active version. Health metrics (latency, error rate, schema compliance) are continuously monitored to determine promotion or rollback.

---

### Capability Broker
The runtime security subsystem within the **Local Daemon** that intercepts, validates, and mediates all privileged I/O requests (Filesystem, Network, Subprocess execution) originating from sandboxed **Runtime** workers against the active **Capability Envelope**. See [ADR 0007](../adr/0007-capability-envelope-and-security.md).

---

### Capability Envelope
A declarative, pre-authorized security boundary policy assigned to a **Workspace Scope** or **Device**. It explicitly lists permitted filesystem root paths, allowed outbound network domains, executable command whitelists, memory limits, and timeouts. Tool candidates operating entirely within the envelope require zero human approvals. See [ADR 0007](../adr/0007-capability-envelope-and-security.md).

---

### Device
The physical or virtual developer workstation (host machine) hosting the **Local Daemon**, local SQLite database, and client AI coding harnesses. Identified by a unique cryptographic device public key in multi-device sync configurations.

---

### Evolution Engine
The autonomous intelligence subsystem (hosted primarily in the cloud evolution plane or optionally via local LLM engines) responsible for analyzing aggregated, sanitized telemetry patterns, synthesizing optimized **Candidate** tool bundles, and generating automated verification test suites.
---

### Gateway (Local MCP Gateway)
The local background MCP server component within the **Local Daemon** that acts as the single unified entry point for all client AI coding harnesses. It handles MCP protocol framing, resolves tool invocations, enforces routing tables, and proxies cloud tools. See [ADR 0001](../adr/0001-v1-topology.md).

---

### Harness Adapter
A dedicated integration module (e.g., `@resin/adapter-claude-code`, `@resin/adapter-codex`, `@resin/adapter-omp`) that normalizes transport differences, configuration formats, and session lifecycles between specific external AI coding harnesses and the **Gateway**. See [ADR 0003](../adr/0003-supported-harnesses-and-platforms.md).

---

### Observer
The local telemetry and monitoring subsystem within the **Local Daemon** that passively captures tool execution events, latency metrics, error signatures, and sequence patterns. It executes the local redaction pipeline to generate **Sanitized Observations** for synchronization. See [ADR 0005](../adr/0005-privacy-data-boundaries.md).

---

### Promotion
The autonomous or manual lifecycle transition where a **Canary** tool version, having satisfied all health and stability thresholds over an evaluation window, is designated as the active default **Tool Version** for the workspace.

---

### Quarantine
An emergency lifecycle state applied instantly to any **Tool Version** or **Candidate** that violates capability envelopes, crashes, fails JSON Schema validation, or triggers health anomalies. Quarantined tools have their routing set to 0% immediately and are isolated from execution.

---

### Rollback
The rapid (<100ms), automated or manual reversion of the active tool routing pointer from a failing **Canary** or degraded **Tool Version** back to the preceding known-good **Promoted** version without requiring daemon restarts.

---

### Runtime (Tool Execution Runtime)
The isolated execution engine (implemented via pinned Deno subprocess workers) that executes tool payload code under strict sandbox flags, memory caps (30MB), execution deadlines (30s), and brokered syscalls. See [ADR 0002](../adr/0002-daemon-and-worker-isolation.md).

---

### Sanitized Observation
A scrubbed, anonymized telemetry record produced by the **Observer** representing a tool execution event or sequence. All API keys, user identifiers, absolute home directory paths, and private source code are removed prior to local persistence and cloud synchronization. See [ADR 0005](../adr/0005-privacy-data-boundaries.md).

---

### Supervisor
The OS-level service manager (`launchd`, `systemd --user`, or built-in supervisor) responsible for keeping the **Local Daemon** running, managing process lifecycles, and restarting failed daemon instances within 500ms. See [ADR 0002](../adr/0002-daemon-and-worker-isolation.md).

---

### Tool Spec
The formal, declarative contract defining a tool's unique identifier, semantic version, human-readable description, input JSON Schema, output JSON Schema, and required capabilities. Conforms to `@resin/contracts`.

---

### Tool Version
An immutable, content-addressed release bundle of a tool comprising its **Tool Spec**, TypeScript implementation bundle, compiled assets, and contract test fixtures. Identified by a semantic version string and content hash.

---

### Traffic Split
A routing strategy used during **Canary** evaluation where incoming tool invocations are probabilistically partitioned between the active **Promoted** version and the **Canary** version (e.g., 90/10 split) to evaluate real-world stability.

---

### Workspace Scope
The root directory boundary of a local software project (containing project files, `.git`, and optionally `.resin/`). All tool activations, capability envelopes, and local telemetry are partitioned and scoped per Workspace Scope.

---
